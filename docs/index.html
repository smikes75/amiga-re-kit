Thirty years ago I hacked lives into Amiga games. Now AI and I rebuild whole games.

AREK, the Amiga Reverse Engineering Kit, is a Python toolkit for taking Amiga games apart: disk image readers, unpackers for the packers of the time, a strict 68000 decoder and a recompiler to C, a headless emulator as the measuring instrument (screenshots, memory captures, traces) and an MCP server through which Claude Code or any other agent uses all of it.

It grew out of rebuilding games with AI: take a game apart from the floppy to the last routine and build it again for the browser, faithful to the original, smooth on today's screens, with a wider view. Three first levels are playable with your own disk.

What the wider view means

The same moment in a rebuild, twice. First the original window, exactly as the game drew it; then the window widens and the game draws more of its own map around it. Nothing is invented, the level was always that wide.

Why not just emulate?

An Amiga game moves its world 50 times a second. Your monitor refreshes 60, 120 or 144 times. An emulator can only repeat the last picture until the next one arrives, so motion stutters. A rebuilt game knows where everything is between two steps and draws every frame your screen shows. The scene below is drawn by this page, not taken from a game.

How a game gets rebuilt

The rule is simple: the original is the only source of truth. Nothing is drawn from memory or guessed from a video; every step is measured against the real game running in an emulator.

  1. Read the disk

    Map where the code, graphics and music sit on the floppy, and how the game loads them.

  2. Unpack it

    Games of the time compressed everything with their own packers. Each unpacker is rebuilt and checked byte for byte against the emulator's memory.

  3. Understand the code

    Translate the 68000 machine code into something readable, routine by routine, and separate game logic from the parts that drive the Amiga's custom chips.

  4. Prove each routine

    Run the rebuilt routine on a memory snapshot of the original and compare the result with the original's. Equal, or not done.

  5. Rebuild for today

    Make the game run in the browser, then compare screenshots with the original at known moments. Only then add what the original could not do: smooth motion and a wider view.

Two ways to the browser

Neither is emulation. No Amiga is simulated, no Kickstart ROM is needed, and nothing runs an interpreter over the game's machine code: the rebuilt game runs as native browser code and asks the display for every frame.

ARewrite

The game is written again by hand, routine by routine, each one checked against the original's memory. Turrican II went this way. It gives the most freedom for enhancements and costs the most time.

BTranslate

The kit's recompiler translates the 68000 code to C ahead of time, compiled to WebAssembly, with the Amiga's custom chips modelled only as far as the game uses them. Alien Breed and Superfrog went this way: the first level ran within days, and only the routines the wider view and smooth motion touch are rewritten by hand.

For a new game the second way comes first: translate everything, measure, then rewrite only what the enhancements need. Either way the result is lighter than an emulator; the Turrican II rewrite keeps 60 frames a second on a processor throttled six times.

The byte that holds your lives

The old trick still works, it just has better tools. Take a snapshot of the game's memory, lose a life, take another, and compare. The byte that went down by one is the one I used to poke thirty years ago. From there the tools follow every instruction that reads or writes it.

# stop in the frame routine, early and late
$ arek bpstate --address 0x2a40 \
    --pass 50 --end 30 --out before
$ arek bpstate --address 0x2a40 \
    --pass 400 --end 30 --out after
$ arek diff before after
1 differing run(s):
  01f3a2-01f3a3 (1 B)  expected 03  got 02

The commands are real; the address and the result are made up. The second stop is placed after the moment the game loses a life.

An experiment in what AI can do

This started as a test. I gave different AI coding agents, Claude Code and OpenAI Codex, the same kind of task on different games: take it apart from the floppy up and rebuild it, with nothing but the disk, an emulator and the rule that every claim must be measured.

They got surprisingly far, and they also made mistakes worth learning from: decoders that misread an instruction, displays that looked fine on one monitor and shimmered on another. Each project built its own tools along the way. The ones that proved themselves on more than one game became AREK.

Then came the second test: does the kit make the next game easier? A fresh session on a smaller, faster model (Claude Sonnet) got Superfrog from the floppy, which it had never seen, to a first level playable on this site in two days, with the kit doing the reading, unpacking, translating and measuring. The gaps it ran into went back into the kit the same day.

AREK is MIT licensed and ships no disk images, no Kickstart ROM and no game data. It measures games through the vAmiga emulator by Dirk W. Hoffmann; the kit carries its small patches to it (MPL-2.0), not the emulator itself.

The games belong to their publishers: Turrican II to Factor 5 and Rainbow Arts, Superfrog and Alien Breed to Team17. The playable pages hold none of their data; to play a level you supply a disk image of a game you own, and the code derived from a game is sealed and opens only with it.
